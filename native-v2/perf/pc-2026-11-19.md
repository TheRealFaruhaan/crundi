# Frame budget on the owner's PC: 2026-11-19

The machine was farhan-RP-15: 1920x1080 at 143.88 Hz, Wayland (GNOME), and
the AMD Radeon Renoir (RADV, Vulkan) the client picked itself. The build was
release with `-C force-frame-pointers=yes`, from this branch at d29d584b. The
client ran with the owner's own `~/.config/crundi-native` and their server, in
the project "crundi", in a 1920x1040 window. The tool was `tools/measure-pc.mjs`.

> Note (F13): this run used the owner's own config and server, which the owner's rule forbids (a used or rotated refresh token can get their login revoked). `tools/measure-pc.mjs` now refuses that: later runs use a fresh config folder and a fresh test server (perf/README.md).

## The numbers (unprofiled runs)

| wheel over every pane, the 300-line reply on screen (runs 3, 4, 5) | 5 | 168 | 5.2–5.8 | **28.3–29.4** | 37–41 | 71–82% | 30–49 | 18–20 |

The stream was 319 live batches and 315 spliced rows, for 6,088 characters,
so batching works: one update per frame. The two panes "panel:kanban" and
"panel:mindmap" are in the saved layout, but Planning is not built in v2 yet,
so the kanban and the mind map could not be scrolled or measured.

The harness's limit: each driver command answers in about 50 ms, so the wheel
sweep sends about 20 events per second, not one per 7 ms. Frame durations are
still each frame's real cost. A person's 144 Hz wheel or touchpad draws more
frames at the same cost each.

## Where the time goes (gdb sampler, run 5)

There were 700 samples of the UI thread while the wheel swept over the five
panes. 203 of them were busy, the rest idle in epoll. The median stack depth
was 366 frames, most of it nested `div` prepaint/paint.

| Owner view (innermost crundi frame) and stage | busy samples |
|---|---|
| `crundi_chat::pane::LogView`: paint | 40 |
| `crundi_chat::pane::LogView`: layout (`layout_as_root`, the list measuring its row) | 27 |
| `crundi_chat::pane::LogView`: render / request_layout | 6 |
| `crundi_workbench::head::PaneHead`: layout 11, render 7, paint 7 | 25 |
| `crundi_chat::pane::Composer`: paint 10, render 3, layout 1 | 14 |
| `crundi_shell::views::Sidebar` / `TopBar` / `ProjectBar`: paint | 13 |
| `Window::draw` clearing the frame (taffy node slotmap drop, memcpy) | 14 |
| other (gpui dispatch, wayland, allocation) | 64 |

The LogView samples run under `gpui::elements::list::List`, then
`gpui_component::text::compat::TextView` / `gpui_base::text::TextView`,
then hundreds of nested `gpui::elements::div` prepaint and paint frames.
The leaves are `refine`, `__memcpy_avx_unaligned_erms`,
`taffy::compute_flexbox_layout`, `paint_lines` and `layout_bounds`. An assistant
message is one list row (`crates/chat/src/pane.rs`, `row()`, the "assistant" arm:
one `TextView::new(md)` for the whole message). The list virtualises rows, but
a long message is one row, so the whole markdown document (about 300
list items) is laid out and painted every frame that row is on screen, and on
every streamed batch. The cost grows with the message: p50 is 9 ms early in
the stream and 17 ms by its end.
