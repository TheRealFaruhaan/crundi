## Where the time goes (gdb sampler, wheel sweep, run 3)

700 samples of the UI thread, 139 busy (`perf/gdb-summary.py`; the full
output is in `pc-2026-11-20/gdb-summary.txt`):

| Where | busy samples |
|---|---|
| inside the scrolled log's `gpui::elements::list::List` (layout 23, render 11, prepaint 4, paint 4) | 42 (30%) |
| **outside the list**: render 31 (Shell `views.rs`, Workbench `lib.rs` 332-396, `mosaic.rs`, ChatPane `pane.rs` 36-37), layout 25, prepaint 11, paint 6, draw 5 | 78 (56%) |
| event dispatch, driver, other | 19 (14%) |

So more than half of each frame is the chain above the log being rebuilt and
laid out again: a notify on the scrolled `LogView` dirties its ancestors
(GPUI marks every ancestor view dirty), so `Shell` and `Workbench` re-render,
and because each pane's body is placed uncached (`workbench/src/lib.rs:331`,
"The body is the kind's layout view (uncached …)"), all the ChatPanes' element
trees are rebuilt and laid out too, for panes that did not change. The median
stack was 242 frames deep (nested `div` request_layout / prepaint).

Where to look (for the owners, not changed here):
- workbench + chat: place each pane's body as a cached view (or make ChatPane
  cached inside it), so a log's notify re-renders only its own pane's chain,
  not its siblings. GPUI reuses a cached child that is not itself dirty even
  when its parent re-renders (only `window.refresh()` turns caches off), so the
  comment's reason for leaving it uncached should be checked.
- workbench: what `Workbench::render` does per frame (the mosaic layout, the
  `frames` map, the measuring canvas, every leaf's div tree) is paid on every
  scroll frame; keep it to the minimum, or keep the dirty path out of it.
- chat log: rows built in `log.rs` 236-254 / 553 show up in render while
  scrolling (new rows coming into view); that is expected, but it is a third of
  the cost.

Crate code (workbench, shell, chat render) is now a few samples. What is left:
- **The log's List** (crates/chat/src/log.rs): every scroll frame the LogView
  is notified, so gpui's List re-renders, lays out (`layout_as_root` per row)
  and prepaints every visible row's element tree. For 300-item replies split
  into block rows that is the biggest single cost. Fewer and cheaper elements
  per row would cut it, and so would not re-rendering the LogView on a pure
  scroll (the list's own scroll offset, without a notify on the view, as
  Zed's editor does).
- **A fixed per-frame floor** in GPUI (present about 16%, clearing the last
  frame about 13%, root layout about 10%), around 2 ms of a 5.7 ms median.
  Only a lighter tree shrinks it.
