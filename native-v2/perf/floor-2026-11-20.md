# The frame floor, 20 Nov 2026 (farhan-RP-15)

What GPUI 0.3.12 costs per frame on the owner's PC, apart from the
client's screens, and what the chat rows add on top. `crundi-v2-floor`
(crates/app/src/floor.rs) opens one 1920x1040 window with no server
and no sign-in. `tools/measure-floor.mjs` sweeps it with the same wheel
as `tools/measure-pc.mjs` (tools/sweep.mjs: one event every 7 ms over a
6x3 grid). Release build, `ZED_MEASUREMENTS=1`.

| mode | what is in the window |
|---|---|
| empty | static text, re-rendered on each wheel event |
| list | `gpui::list`, 2000 fixed one-line rows (13 px, the chat's line height) |
| uniform | the same rows in `uniform_list` |
| workbench | the real Workbench, five panes, each a plain `list` of those rows |
| chatlog | the real Workbench, one chat pane (LogView + Composer), history seeded locally |
| chatlog5 | five chat panes: two 300-item lists, three long mixed-markdown replies |

## On the PC's own display (AMD Renoir, Wayland)

**How these were taken:** by mistake. The runs were meant to go under
xvfb-run, but the shell kept `WAYLAND_DISPLAY`, so GPUI opened each window
on the owner's desktop session. Each window was closed by its PID within
about 15 s. `measure-floor.mjs` now takes `FLOOR_HEADLESS=1`, which drops
`WAYLAND_DISPLAY` under xvfb. The numbers are real-GPU numbers, though not
the Measure step's protocol. They should be retaken there.

| mode | frames | p50 | p95 | max | ≤ 7 ms | renders per frame |
|---|---|---|---|---|---|---|
| empty | 1019 | 1.45 | **1.71** | 6.7 | 100% | empty |
| list | 992 | 3.01 | **4.17** | 5.2 | 100% | rows |
| uniform | 940 | 2.54 | **3.99** | 7.5 | 100% | rows |
| workbench (5 plain panes) | 825 | 3.39 | **5.08** | 7.5 | 100% | workbench, rows |
| chatlog, before | 581 | 4.29 | **6.61** | 7.3 | 99% | workbench, log |
| chatlog, after the slimmer rows | 582 | 4.75 | **5.79** | 8.2 | 100% | workbench, log |
| chatlog5, before (2 runs) | 532 / 550 | 6.33 / 6.51 | **11.03 / 10.35** | 18.9 / 13.0 | 75% / 69% | workbench, log |
| chatlog5, after (3 runs) | 545 / 552 / 514 | 5.80 / 5.99 / 6.36 | **9.92 / 9.30 / 10.32** | 14.5 / 12.5 / 12.9 | 83% / 73% / 60% | workbench, log |

Idle: 0 frames in every mode (4 s each).

## What it says

- **GPUI's own floor fits the budget.** An empty frame is 1.7 ms at p95.
  A full-window list of plain text is 4.2 ms, and five Workbench panes
  of plain text, one scrolling, are 5.1 ms. On this hardware, GPUI 0.3.12
  does not miss 7 ms by itself, so this is no question for the owner.
- **The chat rows are what misses it.** Five chat panes with the same
  layout and scroll cost 9.3–10.3 ms against the plain panes' 5.1 ms:
  about 4–5 ms more, all of it in the scrolled LogView's rows (only the
  Workbench and that one log render per frame) and in replaying the other
  panes' cached paint.
- **Why a scroll rebuilds the rows** (ARCHITECTURE.md, "What a scroll frame
  costs"): GPUI's `list` and `uniform_list` notify the view that drew them
  on each scroll (`list.rs` `StateInner::scroll` ends in
  `cx.notify(current_view)`; Zed's lists behave the same). A cached view
  is reused only at the same bounds, and a row that moved has new bounds.
  GPUI gives no way to move a list's offset without redrawing the LogView
  and its visible rows. Part 2 of the Manager's step cannot be done as
  written: the LogView's own render is a few elements, and the cost is in
  the rows.
- **Every frame also replays the panes that did not change.** For each
  clean cached view, GPUI's `Scene::replay` inserts every primitive (each
  glyph, quad and sprite) again into the scene's bounds tree. That share
  grows with the text on screen across all five panes (in the profile:
  `replay` → `insert_primitive` → `BoundsTree::insert` about 12% of busy
  samples). This is the "frame clear" and "present" share the PC profile saw.

## What changed (crates/chat/src/log.rs)

Each piece of text used to be a div, a StyledText and a canvas that
reported the layout, inside a block div, inside the row's padding div:
five elements for a paragraph, eight for a list item. It is now one
`HitText` (a StyledText that records its layout in its own prepaint) in
one div that carries both the text style and the row's padding. That makes
two elements for a paragraph or a heading and five for an item. The rule
is one 2 px box with a dark top border over the light background, not two
1 px boxes. Its look is unchanged (perf/floor-2026-11-20/chatlog5-after.png).

Result: one chat pane, p95 6.6 → 5.8 ms; five chat panes, 10.4–11.0 →
9.3–10.3 ms. That is real but not enough.

## What is left (for the next round)

Per scroll frame, the scrolled log's visible rows are rebuilt, each laid
out as its own root (`layout_as_root`, about 28% of busy samples), then
prepainted (`prepaint_items`, about 27%) and painted. The next levers, in
the order I would try them:

1. **One custom element per text block** (as Zed's editor and markdown
   preview draw lines): a row's element measures its wrapped lines once
   per width and paints them itself, with no taffy tree per row and no
   div per row. Its size is known from the last layout, so a scroll only
   paints.
2. **Fewer primitives on screen**: no backgrounds or borders a parent
   already draws (the log's `bg` over the pane's `bg`), since each one is
   replayed every frame.
3. Retake these numbers and the PC scenarios on the display, in the
   Measure step, with `measure-floor.mjs` and `measure-pc.mjs` together.

Headless (Xvfb, software Vulkan), every mode draws at 68–80 ms. That is
the software rasteriser, not GPUI, and only the idle check (0 frames) means
anything there.
